How the Website Syncs Itself

Twice a week, an agent reads the club's Google Drive, works out what the public site should say, and opens a pull request. Nothing runs on anyone's laptop. Nothing publishes without a human. And the agent remembers nothing between runs except what it writes down.

What it is

The club's public website is a mirror. Google Drive is where the work actually happens, and the site is a concise, public-facing subset of it that catches up on its own.

The consequence people trip over: you change the site by changing Drive. Project copy hand-edited into the HTML gets overwritten by the next run, with no warning and no record of what was lost. Design, layout and external links live in the repo and are safe to edit there; anything about a machine belongs in that machine's Drive folder.

Why a mirror at all

The alternative is two copies of the truth. Keep project status in both Drive and the HTML and they drift within weeks — then nobody knows which is right, and the site quietly becomes the stale one because it is the copy nobody opens day to day. Making the site strictly downstream costs the ability to fix it by editing it, and buys the guarantee that it cannot silently disagree with the club's own documents.

The sync pipeline, stage by stage

Seven stages inside one GitHub Actions job. The order matters: credentials are separated from the agent, and the agent's work is inspected before anything leaves the runner.

  1. 01

    Trigger

    GitHub's scheduler fires at 13 13 * * 1,4. Cron is always UTC and does not observe daylight saving, so the local slot shifts by an hour in winter.

    .github/workflows/sync-from-drive.yml
  2. 02

    Configuration check

    Verifies the required secrets exist. If they don't, the run logs a setup notice and exits green rather than failing — a missing optional integration is not a broken build, and a red X that means "not configured yet" trains people to ignore red Xs.

  3. 03

    Mirror Drive

    A service account authenticates over a signed JWT and walks the Drive tree, writing each document to plain files in $RUNNER_TEMP/drive. It skips [LR] learning resources and the three finance folders outright — that material is never fetched, so it cannot leak regardless of what the agent decides.

    The script refuses an output path inside the repo, and a mirror of zero files fails the run: an empty mirror would otherwise read as "Drive says nothing" and strip the site.

    scripts/fetch_drive.py — standard library plus openssl, no dependencies
  4. 04

    Record the tree

    The commit SHA before the agent touches anything. Everything the guard checks is measured against this point.

  5. 05

    The agent runs

    Claude Opus 5, up to 200 turns, with a prompt that tells it to read the rules first and restates the publishing constraints inline. It reads the Drive mirror and the current HTML from disk, decides what differs, and rewrites the pages.

    It also prunes its own working memory — see Memory.

  6. 06

    Guard

    A diff against stage 04, restricted to paths the agent must never modify: docs/, .github/, scripts/, mkdocs.yml, README.md, CLAUDE.md, SYNC.md. Any hit fails the run without pushing.

    The prompt asks the agent to stay inside the site. This checks.

  7. 07

    Propose, then announce

    The commit is force-pushed to one reusable branch and a pull request is opened. A later run resets that branch from main and comments on the open PR rather than opening a competing one, so the PR always shows current Drive against currently-published — never a stack of superseded proposals.

    Discord gets the summary and the link. Merging is what publishes; GitHub Pages rebuilds from main in about a minute.

What the agent can actually do

Less than most people assume. The interesting part of the design is everything the agent is not given.

CapabilityGrantedConsequence
Read, Write, Edit filesyesRewrites HTML; edits its own notes
Glob, GrepyesFinds files and content on disk
Bash(git:*)scopedOnly git. No arbitrary shell.
Network accessnoCannot fetch a URL or reach an API
Google DrivenoSees a directory of files, not a credential
SecretsnoNothing to exfiltrate if it misbehaves

It does not scrape the site. It reads the checked-out HTML from disk. It does not query Drive. It reads the mirror fetch_drive.py produced in stage 03, by which point the service-account key is out of scope.

Why the separation matters

Drive documents are untrusted input — anyone in the club can write one, and a document could contain text designed to manipulate the agent. Because the agent has no network and no credentials, the worst outcome of a successful injection is bad HTML. Bad HTML then meets the guard, and if it strays outside the site, the run fails and nothing is published.

Memory: three tiers

Every run is a fresh container. The agent has no recollection of the last one, and no access to the conversation in which any decision was made. Only what is written down survives — and not all of it should survive equally long.

Why observations must expire

Consider a real note: the etcher's timeline document is actually the stepper's, pasted in — do not publish it. That is true today. The moment someone fixes that document, it becomes false, and an instruction that survives its own cause would suppress a perfectly good timeline forever, looking exactly as authoritative as a real rule.

So every entry carries a deletion condition, and the agent evaluates it each run against documents it is already reading:

ObservationRemove when
The etcher's timeline is the stepper's, pasted inits stages describe etching rather than exposure
The tracker names David as etcher owner; the etcher's own doc says TBDa full name appears in the machine's own doc
Spinner and tube furnace link the same diagramthe two docs link different URLs
Sputterer safety section marked "needs advisor input"it no longer says that

The file is capped at twenty entries, so at the cap the agent must drop something rather than grow. And a note it cannot write a removal condition for is a rule in disguise — it flags that for a human instead of promoting it itself.

Guards and trust boundaries

Four independent checks, each covering a different failure. None of them depends on the agent behaving well.

  1. 01

    Material is never fetched

    Finance folders and learning resources are excluded at the mirror stage. The strongest guarantee available: a publishing rule is a request, but bytes that never reach the runner cannot leak.

  2. 02

    The agent holds no credentials

    No network, no Drive access, no secrets. A prompt injection buried in a Drive document has nothing to reach for.

  3. 03

    The diff is inspected

    Modifications outside the site fail the run before the push. The agent cannot quietly rewrite its own rules and make the change stick.

  4. 04

    A human merges

    The final check is a person reading a diff. Everything upstream narrows what reaches that point; this is what decides whether it goes live.

Known limitation

Discord webhook URLs and the service-account key live in GitHub Actions secrets, which any repository admin can replace. The blast radius of a compromised admin account is the club Drive's read access and the ability to post to two channels — worth knowing, not worth further engineering at this scale.

Both systems are unattended, so the interesting question is not whether they fail but whether anyone finds out.

The one gap worth watching

GitHub disables scheduled workflows on public repositories after sixty days without repository activity. This sync deliberately makes no commit when Drive hasn't changed — correct behaviour, but it means a long quiet stretch with nobody touching Drive or the repository could switch the schedule off. GitHub emails a warning first, and any commit resets the clock.

What still runs on a laptop

Two launchd jobs — the original local sync and its watchdog — remain installed on one Mac. They were the whole system before the cloud migration and are now redundant. They stay only until the cloud sync has run unattended on its own schedule; keeping a working fallback while the replacement is unproven is cheap, and deleting it first is how you end up with neither.

Why the laptop had to go

launchd does not wake a sleeping Mac; it runs a missed job at whatever wake happens next, which on a sleeping laptop is a maintenance wake lasting seconds. On 27 August a run started during one of those, held no power assertion, and the machine slept underneath it mid-request. Scheduled execution on a laptop is best-effort by construction — which is the entire argument for moving to hosted compute.
